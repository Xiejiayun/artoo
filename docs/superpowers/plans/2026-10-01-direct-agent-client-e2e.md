# Direct agent conversation client E2E plan

> Execution: bounded fixture, native driver and installed-Mac driver work; root
> owns integration, real-client E2E, screenshot review and staged main pushes.

**Goal:** Exercise the existing direct-agent conversation, automatic waiting
recovery, explicit failed-turn retry and running-turn cancellation through
native iOS and the installed Mac application.

**Architecture:** Reuse the authenticated server, node WebSocket and production
process adapter. A deterministic CLI subprocess generates actual answers and
controlled failure/hold behavior. APIs prepare disposable resources or read
evidence; client UI sends requests and performs Retry/Cancel.

**Technology:** SwiftUI/XCUITest, Electron/Playwright, Node 24, existing
assistant-turn services and context-pack receipts. This plan does not establish
external model quality or deployed authentication.

## Verified lifecycle constraints

- `apps/server/src/services/assistant-service.ts` scans queued/waiting/running
  turns every 1.5 seconds. A waiting turn automatically resumes when a worker
  returns; clicking Retry after reconnection would race that automatic path.
- Failed turns are not automatically dispatched. Retry preserves turn and
  user-message identity, clears the old run association and requeues the turn.
- Cancelling a running turn stops the real worker process before confirming
  cancellation. Check process termination and absence of a completed answer.
- Native **Retry pending send** concerns uncertain HTTP delivery. It is
  distinct from the agent-turn Retry operation in this plan.

## Required scenario

| Request | Driver actions and actual environment | Required evidence |
| --- | --- | --- |
| First turn | Stop the real worker; select the agent and send through UI; observe waiting, then restart the worker without Retry | No run while waiting; one automatic dispatch; first answer generated by the CLI |
| Follow-up | Send another request through UI; its first CLI launch fails; retain failed state for at least two dispatcher periods; use that turn's Retry | Same turn/user message, a new run, and the successful CLI reads and repeats the actual first answer from context |
| Hold and cancel | Send a request whose CLI writes a startup receipt and stays running; observe running and the live PID; Cancel through UI | Same run/turn cancelled, process terminated, no third agent answer and no later redispatch |

Expected totals: three logical turns, four subprocess launches, two agent text
answers; two completed runs, one failed run and one cancelled run. Match exact
instance/computer, turn/run/response IDs, receipt PIDs and context message
IDs/body hashes. The current request and future requests must not leak into
prior-history context.

## Suite and reporting requirements

The current seven-case native run is about 14 minutes. The Xcode invocation
limit is 20 minutes, the parent child-process limit is 30 minutes, the existing
browser-flow wait is 20 minutes, and the iOS CI job limit is 45 minutes. Do not
append more workflows without separating scenario ownership.

- [ ] Introduce explicit allowed `core` and `assistant` selections (with an
  aggregate `all` runner), each mapped to exact `-only-testing` method names.
  The assistant harness must not launch browser observers waiting for core
  chat/revocation signals or execute unconditional core verification statements.
- [ ] Give each suite its own xcresult, exported attachments and HTML. Record
  the selected suite, expected/actual case IDs and passed/failed/skipped counts.
  A successful assistant subset must never be reported as the full native suite.
- [ ] Aggregate only matching-source core and assistant results. Retain each
  failed attempt, real captures, explicit fixture scope and cleanup status;
  pairing inputs and fixture credentials stay out of the shareable HTML.

Implementation and real-client verification are in progress. The separate
integration plan and timestamped reports distinguish executed failures,
verified subsets and full matching-source results; this plan alone is not
a passed native or installed-Mac scenario.

Production conversation context contains task/run headers, project/workspace,
room/turn/current request and prior messages. It does not contain the current
computer/instance identity. The fixture must report only identities it actually
observes; the driver binds those receipts to exact computer/instance values from
the resulting server run. Start with a separate empty top-level conversation:
the first request has no prior history, the second has the actual first request
and answer, and the held third request has both completed exchanges. Future
thread coverage must be explicit rather than inferred from this empty-room case.
