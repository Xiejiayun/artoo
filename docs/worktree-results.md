# Node-owned Git results

The node-local executor consumes contributions from separate worktrees and verifies exact sealed results with protected commands. A separate managed path now connects an explicitly assigned plain-result task to node-owned author/finalizer execution, durable event delivery and server acceptance. GoalRunner, product-stage measurements, independent review and publication do not yet consume this path. Existing ordinary-workspace execution keeps its current behavior; a remote payload cannot create local execution authority.

The executor lives in `apps/artood/src/owned/worktree-results.ts`. Its explicit local profile fixes the node, project, repository, baseline commit, content paths, state directory, allowed roots and Git executable. It supports Linux/macOS, a non-bare repository with an existing baseline commit, bounded regular-file content and two-input merges. An empty newly initialized product repository still needs a controlled initial commit before this executor can be wired into that product flow.

## Authority and results

`openOwnedWorktreeResults(profile, { mode: "create" | "open" })` returns these local operations:

| Operation | Input and result |
| --- | --- |
| `capture` | A genuine materialized worktree, admission, run handle and original authenticated closure observation produce a sealed result reference. |
| `merge` | Two exact local result references produce a merged candidate or a recorded conflict. |
| `materialize` | A result/conflict reference produces a new worktree and a new in-memory execution handle bound to that input. |
| `materializeForVerification` | An exact result reference produces a fresh private verification checkout and an opaque token; its writer-capable handle remains internal. |
| `resolve` | A new owned writer on the materialized conflict produces a repaired candidate. |
| `read` / `conflict` | Revalidate stored references, private refs, immutable Git objects and content manifests. |
| `lookupVerification` / `readVerification` | Authenticate a saved verification intent or final receipt and its immutable result; historical reads grant no execution or delivery authority. |
| `inspect` | Read a historical operation phase; this does not restore execution authority. |

The sealing boundary checks that the original physical closure observation belongs to the exact admission, run handle and worktree. It also waits for workspace/research tools to close. CLI process closure alone can precede tool closure. A copied receipt, a retained directory, a model answer or artifact metadata cannot supply this authority. Physical receipt time and the later result-closure check time remain separate observations.

The node writes blobs, a private index, trees and commits without moving the author's HEAD or index. It records scoped file bytes, executable flags and empty directories; `.gitignore` does not choose the result scope. Files outside the configured content paths retain their fixed-base version. Inputs and outputs are bounded to 512 manifest entries and 8 MiB of scoped file bytes. Unsupported links, attributes, submodules, repository configuration and ambiguous directory merges fail closed.

Stored records bind the repository and profile, request, author identity, input references, base/parents, commit/tree, content manifest and actual Git subprocess closure observations. A private create-only ref preserves the object. Protected local state has authenticated records and checked ownership, permissions and directory identity. This assumes a trusted node administrator and cooperating runtimes; it is not a sandbox against the node's OS identity.

Request IDs are immutable. Repeating the same capture or resolution with the same content returns the original receipt. Changing file bytes, empty directories, executable flags or other request inputs rejects that replay. Restoring the original content permits the same original result to be read again; reading a sealed reference never substitutes current workspace files for its immutable content.

## Conflicts, concurrency and restart

Real Git merges operate on fixed commits. An unresolved conflict is persisted with base/ours/theirs, conflict paths and a candidate snapshot. It remains a conflict until another genuine owned writer changes the materialized conflict and closes. Removing conflict markers is only a prerequisite for sealing a candidate; meaningful tests and independent acceptance are still required later.

A create-only lease in the repository's common Git directory permits one executor operation at a time across instances/processes. Concurrent operations receive a busy error before beginning; a later retry can use the same request ID. This is serialized integration, while authors may work in separate worktrees.

A normal restart can authenticate sealed results and create new consuming worktrees. It cannot recreate an in-memory execution handle for an already materialized directory. Unknown Git closure or an interrupted executor retains its lease and state. There is currently **no automatic stale-lease recovery**, and reopening/consumption remains refused while that lease exists. Do not delete the lease merely because a PID is absent. Full autonomous interruption recovery is still required before this becomes an unattended GoalRunner path.

## Protected verification of an exact result

`apps/artood/src/owned-worktree-verification.ts` prepares a version 1 node-local template and exposes `verifyOwnedWorktreeResult`. The protected template binds the node, project, result-store profile digest, repository, allocation base, commands and complete subject paths. Remote task text cannot choose these commands. Only the original prepared template object grants authority; serialized metadata does not.

Verification materializes a fresh checkout from the sealed result. It holds the repository lease through the real verifier process and checks the genuine checkout, immutable Git result and full content manifest before and after execution. A verification materialization has a distinct durable request kind, so replaying its public fields through the writer API cannot expose its hidden handle. A busy repository leaves an unused token available for an exact retry; unknown verifier closure retains the lease.

Returned evidence separately records the template digest, result reference/commit/tree/manifest and ordinary verifier profile/subject digests. The ordinary profile digest still includes its physical workspace root. Neither a template digest nor a result manifest digest substitutes for it. Plain protected commands are supported; capability-bound browser measurement, review and release are explicitly rejected in this local slice.

`verifyOwnedWorktreeResult` retains its in-memory return behavior. The optional `verifyOwnedWorktreeResultDurably` path records an exact intent and context digest, then synchronizes the allocated verifier's actual profile and subject before running commands. After confirmed closure and the complete result postcheck, it authenticates the original node-issued evidence object and seals a signed receipt in the existing result store. It uses no additional delivery journal. Copying an evidence object or a lookup response cannot create a receipt.

A receipt reference binds the complete canonical receipt. Exact replay can return the saved historical result without running the verifier again. A new process can read it after authenticating the signed record and immutable Git result; it cannot recover the old target or writer handle. Known failed/cancelled commands can have historical receipts whose failure outcomes remain unchanged. Failed postchecks produce no final receipt. Unknown process closure or persistence/cleanup failure retains the repository lease. A crash after final sync but before lease cleanup therefore still requires separate recovery; the receipt alone cannot release that lease.

The standalone receipt API does not dispatch runs or settle a managed journal. The managed task path below adds node advertisements, dispatch, durable delivery and server acceptance using separate versioned contracts. A mismatched genuine template/store is rejected before verifier execution, but its unused checkout may already have been created. Plain protected commands remain the supported scope; independent product review and publication are not enabled.

## Public evidence from an authenticated local result

`describeOwnedResultProfile` derives bounded routing metadata from the original opened result store and prepared verifier template. `projectOwnedResultVerification` authenticates a saved receipt and its exact authored input under the repository lease, then produces the version 1 domain evidence contract. Neither operation advertises or activates a node capability. The contract accepts plain command verification without verifier ContextPack; it does not accept product-stage, browser, research or review contexts.

New captures can contain an optional versioned launch proof. The adapter snapshots the actual start before asynchronous preparation and records the rendered context file's initial bytes immediately before spawn. The result store signs this proof only when the actual start matches the allocation binding and original closed writer. The original ContextPack digest and rendered-file digest have separate meanings; neither proves that a model read the context. Legacy captures remain readable but cannot acquire this proof retrospectively.

Projection compares the signed source proof with the expected author assignment, exact input result, selected template and physical verifier execution. Captured private store readers prevent replacement of public methods from manufacturing evidence. A new process can project an authenticated historical receipt without reconstructing writer authority. Copies and deserialized projections cannot pass the local original-object authenticator. The managed task path below now supplies transport authentication, persisted server assignments and event acknowledgement for explicit plain-result tasks; projection alone still grants none of those authorities.

## Managed plain-result task execution

The protected local profile loader prepares genuine result stores and verifier templates, then the managed handshake advertises their bounded descriptors as `owned-result-run.v1`. This integrated configuration currently requires the qualified macOS journal implementation and an explicitly upgraded v4 journal. Store initialization and journal upgrade are offline operations; startup does not create, reset or silently migrate them. The standalone result executor's Linux support does not enable the managed Linux path.

An authorized caller can explicitly assign a ready task through `POST /api/v1/tasks/:id/assign-owned-result`, selecting the installed result/verifier profiles and either the baseline or one exact accepted predecessor run. The server persists the complete immutable assignment and sends `run.start.owned-result.v1` with the original start identity. The node performs the genuine author execution, capture and protected verification in a fresh checkout. Its original controller remains bound through finalization and closed delivery. Ordinary commands and the original initiating user's authorization remain separate.

The node-owned `run.owned-result.verification`, completed retention and terminal event are committed in order. The server persists each qualified receipt before acknowledging it; successful terminal delivery waits for accepted evidence and retention ACKs. Explicit task acceptance records the exact passing result evidence, and a later accepted-run input rechecks that binding. This is a task-level acceptance path, not the existing autonomous independent-review workflow.

GoalRunner still assigns ordinary workspaces. The version 1 owned-result contract deliberately rejects product-stage, measurement/capability and review contexts, and the static publisher does not consume managed per-run results. Local merge/conflict operations therefore still need a consuming scheduler and product acceptance path. The earlier stale-lease and uncertain-interruption limits remain unchanged.
