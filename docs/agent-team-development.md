## What makes the agents a team

- Planning is a multi-agent discussion that produces a stage-labelled task graph. Every later stage must wait for all tasks in its preceding stage. Invalid JSON, missing stages and invalid dependencies feed a bounded re-synthesis with concrete diagnostics.
- At least two distinct agent identities contribute. Role assignments are persisted, with research requiring actual `research.web` availability. Research, design, implementation and validation use the shared reserved physical workspace. Execution is currently sequential to keep a single integrated source tree; there is no cross-worktree merge consumer yet.
- Each task's context includes the objective, accepted plan, accepted predecessor artifacts and stage instructions. The files below provide inspectable handoffs rather than relying on an ever-growing conversation history.
- Team contexts pin the accepted research report before design, and both research and design before implementation/validation. These fixed file paths and checksums come from the accepted run's node-owned `required_files` measurements, not artifact metadata. The node checks them before author execution and around verification; the server also compares the receipt to the pinned inputs. Removing requirements or weakening browser assertions cannot pass acceptance. Missing measurements fail closed; changing an accepted specification requires a separately reviewed plan revision. Multiple tasks within one stage produce one final stage handoff, taken from that stage's last accepted execution.
- Team planning and stage dispatch require the current node's `product-stage-verification.v1` capability. A legacy verifier cannot silently ignore the new input pins; ordinary manual and original single-agent goals retain their existing compatibility rules.
- After the author finishes, the node runs its protected verifier. Another identity then performs a restricted read-only review of that exact source version. The review run has its own node verification requirement, including the expected source digest. Acceptance requires matching profile/source/required-file evidence and a structured verdict referring to the original run and evidence.
- A reviewer cannot replace node measurements with prose or an artifact called `test_result`. A changed source, failed check, missing receipt, wrong reviewer, stale verdict or blocking finding prevents acceptance. Failure feedback reaches correction runs. Auxiliary review processes are included in pause, cancellation and uncertain-disconnect handling.
- Planning and review assignments persist a `prepared` dispatch intent in the same transaction as the run. The sender records `exposed` before touching the transport. A still-prepared intent can be delivered after recovery; an exposed or legacy intent on a new binding is probed through the existing process-recovery path, rather than treated as work that never started. Repeated starts on the same live binding retain the original run ID. This is conservative recovery, not an exactly-once provider-execution guarantee across daemon restarts.
- Final publication is separate from task execution. A successful task graph cannot complete a publication goal without a matching deployment receipt. See [target-product publication](product-publication.md) for immutable artifacts, endpoint identity, restart replay and rollback.

## A reusable static-web acceptance program

`apps/artood/dist/web-acceptance-cli.js` is a protected verifier for self-contained static web products. Install Chromium for the verifier's service account using the pinned Playwright version (`npx playwright install chromium`), or supply an installed browser executable in the protected JSON configuration. On Linux, install the browser's system dependencies and run the worker with a functioning Chromium sandbox. Browser installation and credentials are node setup, not model-controlled task commands.

Example `/opt/artoo/web-acceptance.json`:

```json
{
  "evidence_root": "/var/lib/artoo/browser-evidence",
  "action_timeout_ms": 5000,
  "viewports": [320, 390, 768, 1280],
  "design_capture_cases": true
}
```

The optional `browser_executable` must be an absolute path outside the product workspace. The evidence root must already exist outside that workspace. Protect this configuration, the verifier installation and evidence directories from coding runtimes and other writers. The generic program supplements the node's source receipt and stage provenance checks; it is not a universal proof that every subjective product requirement was satisfied.

Example verifier profile:

```json
[
  {
    "id": "default",
    "project_id": "proj_product",
    "workspace_root": "/srv/artoo/products/journal",
    "commands": [
      {
        "id": "static-web-acceptance",
        "argv": [
          "/usr/local/bin/node",
          "/opt/artoo/apps/artood/dist/web-acceptance-cli.js",
          "/opt/artoo/web-acceptance.json"
        ],
        "timeout_ms": 600000,
        "observation": {
          "format": "static-web-acceptance.v1",
          "evidence_root": "/var/lib/artoo/browser-evidence",
          "capabilities": { "version": 1 }
        }
      }
    ],
    "required_files": [],
    "subject_paths": ["product", ".artoo/product"]
  }
]
```

Research checks structured requirements. By default, design opens the actual prototype, while implementation and validation execute each design case's `browser_steps` at 1280px and 390px. The protected configuration above explicitly selects four widths and also executes the cases during design. This setting requires the prototype to support those interactions; it does not turn a rendering-only result into a functional pass. Cases must begin with local navigation and contain a content/value/count assertion. Supported actions are navigation, reload, click, fill, check and fixed DOM assertions. The program accepts no JavaScript, shell commands or external target URLs from the case. Each case uses a fresh browser context; local storage persists within that case, allowing a real save/reload assertion. It rejects missing titles/content, horizontal overflow, unnamed interactive controls, JavaScript errors and external requests. These checks cover basic usability and accessibility, not a complete accessibility audit.

Each case screenshot records the visible viewport after its final browser step, at the configured width and the current 900px height. Native scrollbars remain visible and the capture does not resize the page or change product CSS. This is not a full-page screenshot or proof that content below the fold was visually inspected; all declared browser steps and the page checks still execute before capture.

Screenshots and result JSON are stored beneath a hash of the verification request ID in the protected evidence root, without overwriting an earlier request's evidence. The program leaves the measured workspace unchanged. Chromium is launched directly in the verifier's process group rather than using Playwright's detached launcher; actual exit is required before cleanup, and the outer node controls timeout/cancellation of the group. Browser request routing blocks page HTTP(S)/WebSocket traffic outside the product origin; this is not an OS network namespace or firewall guarantee. Browser results are actual executions, while the independent reviewer remains responsible for assessing whether the proposed cases sufficiently cover the objective. The static release profile should use `output_path: "product"` for this layout. A built framework app using a separate output directory requires an appropriate verifier/profile; do not silently certify a different directory.

The optional command `observation` configuration is part of the protected profile fingerprint. It enables typed node observations of actual stage, cases, widths and assertion counts. After confirmed process closure and source/profile revalidation, the node seals the result and screenshots into a request/profile/source/check-bound bundle. Authors can read their preview evidence through `read_evidence({reference})`; independent reviewers receive only authenticated final observations and a read-only evidence bridge. References are opaque and session-scoped. The reader accepts no filesystem path, URL or command and rechecks file types and hashes. Evidence stays outside the measured source tree.

Profiles without an observation format retain their prior verification behavior and report unknown execution scope. Declaring the format but returning malformed output, a different stage, or unverifiable evidence fails verification. Raw preview diagnostics are bounded and redacted; they cannot replace final node evidence. Case execution and screenshot existence do not establish that every requirement was satisfied. For example, an ordinary single-page case does not prove a two-tab conflict scenario, and basic accessible-name checks do not prove screen-reader or keyboard behavior.

### Optional v3 storage fault windows

Protected v3 configurations can opt in with `storage_fault: { version: 1 }`. The advertised contract then contains the initializer digest, exact fault entries and measurement limits. A design case requests this measurement through a versioned `storage_checks` sidecar; merely mentioning storage in a task cannot enable it. Without a sidecar, no storage controller is installed and no storage observation is emitted. V1, v2 and unopted v3 profiles retain their previous serialization and meaning.

Two fixed synthetic exceptions are supported:

- `read-security`: the current document's `Window.localStorage` getter throws `SecurityError`. Cached `Storage` objects are outside this guarantee.
- `write-quota`: the `Storage.prototype.setItem` entry throws `QuotaExceededError` for local storage. This is not actual disk exhaustion and does not cover every write path.

A sidecar has one to four sorted, nonoverlapping windows. Each names its mode, `arm_before_step`, `settle_after_step`, exact `requirement_criteria` references and the `ui_assertion_steps` that must succeed inside it. `min_hits` is fixed at 1; `native_storage` is `{ scope: "all", comparison: "sampled-equal" }`. Fault cases use only `main`, cannot create other realms or pages, and permit document changes only through explicit `navigate`/`reload`. A window spans one document and may navigate only on its first step. Other cases may still use ordinary v3 multiple-page programs.

The first window at step zero samples native storage during the first product document's protected pre-script pause. Later windows sample before their action, including before leaving the old document on reload. Actual fault hits, successful declared UI assertions and identical native before/after entries are required. Snapshots are bounded to 512 keys and 1 MiB of UTF-8 key/value bytes. Observed mutations fail, including an observed write followed by restoration; at most 512 mutation events are admitted per case. Event coverage is explicitly `observed-only`: zero observed events does not prove complete absence of mutations throughout the interval.

Traces contain snapshot digests/counts, fresh-hit counts and the measured install/arm/settle/disarm sequence, with no raw storage values. The node independently reconstructs the sidecar plan and binds it to the protected initializer digest and source. Report/observation data is the single compact projection of the sealed trace. Authors can inspect preview evidence; independent reviewers receive final evidence through the existing checksum-bound trace and PNG reader. A model-provided counter or copied initializer cannot authorize a passing receipt.
