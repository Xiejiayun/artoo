# 消息状态对账与批次协商

`GET /api/v1/bootstrap` 可选返回 `message_sync: { version: 1, visibility_batch_limit: 500 }`。该版本化能力只扩大 `POST /api/v1/rooms/:id/messages/visibility` 的标识符数量上限，不改变请求/响应字段、权限或消息移除判定。新服务端最多接受 500 个长度不超过 160 的非空 ID；旧客户端仍可发送最多 100 条的批次。

Web 读取当前 bootstrap 缓存中的能力。字段缺失、版本未知或数值不符合 v1 时，保持原有 100 条批次；有效 v1 使用其有界值（最高 500）。未获得能力时不会向旧服务端发送大批次。请求仍逐批执行，任一失败均保留错误提示和重试入口，不把失败视为消息仍可见的证明。

每次刷新继续拉取增量、必要时追赶多页，并检查全部已缓存消息和独立根消息 ID。首次、重连、`sync.required`、降级轮询和手动重试均执行 HTTP 对账；不把 WebSocket connected 当作订阅或追赶完整的证明。

## 可选紧凑状态 v1

bootstrap 的 v1 能力可另含 `reconciliation_version: 1`。只有完整、已知的能力才使用 `POST /api/v1/rooms/:id/messages/reconcile`，请求为 `{ version: 1, message_ids: [...] }`，最多 500 个长度 1–160 的 ID；使用与可见性接口相同的组织/房间授权。响应为 `{ version: 1, states: [...] }`，对每个唯一请求 ID 返回一次：

- `visible` 或 `removed`：`{ id, status, reply_count }`，移除依据为受保护的两列，绝不依据用户 payload。
- `unavailable`：`{ id, status }`，未知、其他房间及其他组织的 ID 相同，不返回正文、计数或其他元数据。

客户端验证版本、数量、唯一性、精确 ID 覆盖、状态和非负安全整数计数。缺项、重复、额外 ID 或无效结构均报告同步失败；`unavailable` 也报告错误，不伪造为管理员移除。完整响应内确认的移除仍会持久记入客户端。每批完成或失败时立即刷新该房间全部列表、线程和单消息缓存，避免后一批失败让已确认移除的正文继续显示；错误仍可见，重试仍从全部缓存 ID 开始。

紧凑状态成功后，计数与移除均已有 HTTP 权威结果，普通根消息刷新可省额外最新 50 条正文快照。协议缺失/未知时保留旧路径；请求失败时保留错误，不将失败当作同步成功。旧版 agent 文本可能在后续读取时动态补出历史计划预览，因此缓存或本轮增量中存在未有有效预览的 agent 文本时，保守保留原快照；线程增量原有投影也保持。此优化不依赖在线状态，断连后无新根消息也能校正计数。

写入路径的回复数只递增。对账响应和增量页不会覆盖等待期间通过实时事件取得的更高计数；合并前读取最新缓存，保留并发加载的历史、分页游标和移除标记。

## 验证范围

真实组件查询缓存夹具有 250 条消息、空增量、离线期间变化的根回复数及旧历史移除。消息同步相关请求计数如下（不包含 bootstrap、成员和其他业务查询）：

| 场景 | 无能力/旧服务端 | v1 / 500 |
| --- | ---: | ---: |
| 房间根列表刷新 | 1 次增量 + 1 次根快照 + 3 次可见性 = 5 | 1 次增量 + 1 次根快照 + 1 次可见性 = 3 |

回归确认两种情况均核对全部 250 个 ID、显示更新后的 7 条回复计数、保留先前分页游标，并在后续无新消息的失效刷新中继续保持移除标记；另验证可见性失败后完整重试。现有并发历史加载与分页测试保持。服务器在真实 PGlite 中验证 500 个唯一 ID 的移除结果、501 条拒绝、房间边界及受保护移除字段；API 客户端验证 500 条请求后的持久移除标记。

上述第一阶段计数来自组件 API mock，不能视为耗时。后续紧凑状态、实际 HTTP 测量及真实浏览器验证见 [P5 测量记录](message-reconciliation-performance-2026-11-13.md)。最终统一 E2E 和真实 Provider 验收分别记录。
