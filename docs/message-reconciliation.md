# 消息移除对账与批次协商

`GET /api/v1/bootstrap` 可选返回 `message_sync: { version: 1, visibility_batch_limit: 500 }`。该版本化能力只扩大 `POST /api/v1/rooms/:id/messages/visibility` 的标识符数量上限，不改变请求/响应字段、权限或消息移除判定。新服务端最多接受 500 个长度不超过 160 的非空 ID；旧客户端仍可发送最多 100 条的批次。

Web 读取当前 bootstrap 缓存中的能力。字段缺失、版本未知或数值不符合 v1 时，保持原有 100 条批次；有效 v1 使用其有界值（最高 500）。未获得能力时不会向旧服务端发送大批次。请求仍逐批执行，任一失败均保留错误提示和重试入口，不把失败视为消息仍可见的证明。

每次刷新继续拉取增量、必要时追赶多页、核对最新根消息回复数，并检查全部已缓存消息和独立根消息 ID 的移除状态。首次、重连、`sync.required`、降级轮询和手动重试都沿用原有对账路径；没有仅凭 connected 跳过根快照或移除核对。稳定连接期间减少根快照仍需要更完整的同步状态证明，本项选择先合并安全的可见性批次。

## 验证范围

真实组件查询缓存夹具有 250 条消息、空增量、离线期间变化的根回复数及旧历史移除。消息同步相关请求计数如下（不包含 bootstrap、成员和其他业务查询）：

| 场景 | 无能力/旧服务端 | v1 / 500 |
| --- | ---: | ---: |
| 房间根列表刷新 | 1 次增量 + 1 次根快照 + 3 次可见性 = 5 | 1 次增量 + 1 次根快照 + 1 次可见性 = 3 |

回归确认两种情况均核对全部 250 个 ID、显示更新后的 7 条回复计数、保留先前分页游标，并在后续无新消息的失效刷新中继续保持移除标记；另验证可见性失败后完整重试。现有并发历史加载与分页测试保持。服务器在真实 PGlite 中验证 500 个唯一 ID 的移除结果、501 条拒绝、房间边界及受保护移除字段；API 客户端验证 500 条请求后的持久移除标记。

本地组件测试使用明确的 API mock 测量请求次数，服务端测试使用真实数据库；没有测量生产 HTTP p95 或网络延迟，也不以减少请求数推断具体耗时收益。最终统一 E2E 和真实 Provider 验收分别记录。
