# Internal application data wire v1

This is an unintegrated framing/DTO component for the future trusted proxy and LPAC bootstrap. It starts no process, opens no pipe or socket, accesses no database, grants no capability, and is not referenced by node admission or the installed native helper.

Each original directional stream uses a separate encoder and decoder. A frame is a four-byte unsigned big-endian byte length followed by UTF-8 JSON. The strict envelope has `version: 1`, a sequence beginning at 1 and incrementing by one, and the fields for one allowed message. Invalid UTF-8, BOM-prefixed JSON, malformed JSON, unknown fields, wrong direction/version, a sequence gap/replay, and truncated input fail the instance permanently. Later calls preserve the first fixed error code without reflecting source text, paths or raw exceptions. A sequence detects ordering only within this decoder lifetime; it is neither authentication nor cross-restart idempotency.

The host-to-application messages are `invoke`, `data-result`, `data-error`, `cancel` and `shutdown`. Application-to-host messages are `response` and `data-call`. Call and data-call IDs are bounded correlation strings. There is no ready, verification, cleanup, process-exit, publication or authority message. A shutdown frame ends only the host's command stream; the reverse stream may still drain. Decoder `finish()` records only that its caller declared framing EOF with no partial frame. Neither fact proves an original pipe EOF, process exit, empty Job or safe storage deletion.

`ApplicationWireEncoder.encode()` accepts JSON text containing the message fields, without version/sequence. It parses and validates that text, assigns its own sequence and returns framed bytes. It does not serialize caller objects, so getters or `toJSON` hooks are not an execution path. `ApplicationWireDecoder.push()` accepts a byte slice and returns deeply frozen DTOs; it never retains an input-buffer alias. If a later frame in the same call fails, that call returns no prefix frames and becomes terminal. No consumer callback runs inside decoding. A future owner must serialize stream delivery, discard a failed connection, enforce output/backpressure/total-rate limits and avoid unbounded retention of returned arrays.

The retained incomplete binary buffer is at most 1 MiB plus a four-byte header. Each caller-supplied chunk is at most 64 KiB; the future transport must split a larger OS read into slices before calling `push`. A push can finish one previously buffered frame plus frames contained in that bounded slice; returned frames are not retained by the decoder. Per-frame parsing is bounded by the frame size, nesting depth 32, 16,384 total values/object keys, 128 entries per object and 1,024 entries per array. The encoder and decoder count the complete envelope, including the host-owned version and sequence fields, against the same entry budget. Nesting is checked before JSON parsing; the parsed graph is then counted and frozen iteratively. These bounds are not hard process memory, CPU or wall-time confinement, nor a lifetime output quota.

The request/response field shapes match the internal SDK draft, with a deliberately finite supported JSON subset: numbers must be finite, strings and keys must have valid Unicode, and the bounds above apply. A request/response body is at most 256 KiB when JSON-serialized. Requests allow GET/POST/PATCH/DELETE; responses allow the SDK's fixed status set, with a null body for 204. Query dictionaries contain at most 32 bounded key/value pairs. A request path is a bounded origin-relative HTTP route composed of literal ASCII segments; schemes, authorities, escapes, query strings, backslashes and dot segments are rejected. This field is never an OS path or target URL. The future proxy must still enforce the actual listener identity, Host/Origin rules, authentication and route semantics.

`data-call` contains only correlation IDs and `request_json`, capped at the existing broker's 64 KiB request bound. `data-result` contains a `reply_json` string capped at its 256 KiB reply bound. Both nested texts must be bounded JSON objects, but this component intentionally does not certify their broker schema or provenance. The future trusted host must parse every call with `parseApplicationDataRequest()` using its own schema, bind it to a live invocation, authorize the exact request digest/scope with an original broker permit, apply global read-only/service-generation policy, and revoke/drain that invocation at cancellation/completion. It must not infer write authority from method, route, call IDs, sequence or app-supplied fields. The application cannot put scope, permit, argv or OS path fields in the envelope. Arbitrary business JSON remains data; words inside it do not confer permissions. Host-owned reply scope is informational and cannot be replayed as a permit.

The fixed `data-error` codes match the broker's non-secret codes. No raw error message, SQL, stack, credentials or arbitrary diagnostic field crosses this format. Native data-pipe ownership, bootstrap behavior, active-call correlation, per-invocation data-call limits, cancellation races, timeout/closure, HTTP publication, broker process IPC and release recovery are still unimplemented. This protocol alone does not isolate generated JavaScript or make any application runnable.

The tests cover single-byte framing and Unicode splits, multiple frames/partial headers, buffer-alias isolation, every host message kind, direction/field/version forgery, byte/depth/entry limits, malformed Unicode/JSON, truncated EOF, current-stream sequence replay, post-shutdown/post-EOF rejection and the JSON-text-only encoder boundary.
