# Trusted application broker process

This component is being integrated and is not an advertised application capability. It executes only the fixed trusted broker bundle. Generated JavaScript still requires the separate LPAC owner and its closed qualification gate; it is never passed to this ordinary-token broker launcher.

The dedicated Windows owner reuses the existing native daemon supervisor with `maxRestarts: 0` and lifetime Job ownership. It keeps the original helper process and its pipes. The native supervisor pins the Node executable, complete single-file broker bundle and configuration, creates the target atomically in its original Job, and retains the original target HANDLE. There is no PID adoption, Worker substitute or ordinary `spawn` fallback for the target. No native protocol, helper binary or existing daemon behavior is changed.

Only the trusted host holds broker stdin. The pinned configuration fixes the database path, schema, product/artifact/data/service scope and maximum access. Host control commands start, cancel and expire invocations; generated-process bytes are carried only in a `receive` command. Bytes inside that field cannot become a host command. The generated process must never receive this control channel. Health and peer use require a separate broker process configured with maximum read access; a writable broker rejects those purposes.

Control commands have strictly consecutive sequence numbers and strict fields; each reply binds that exact command sequence. The native supervisor has its separate ordered frame sequence. The owner admits one command at a time and sends at most one 16 KiB native input chunk at a time. Each chunk must receive both its exact command ACK and the generation-0 `daemon_input_written` byte count before the next chunk. The ACK alone only means enqueued. The owner bounds chunks, control commands and cumulative bytes below the existing supervisor's 4,096-control and 16 MiB-output limits. The broker bounds input lines, total input/output and invocation state. A result may contain at most 256 data frames (eight live invocations times 32 calls); the unchanged byte limits also apply. There is no unbounded write queue. The original process lifetime is fixed at 180 seconds, so this component is a bounded session rather than a persistent service.

Normal stop first arms native graceful stop and waits for that exact ACK, then sends the broker shutdown command. The broker revokes its bridge, closes SQLite, flushes its final reply and exits. The host does not close helper stdin early: native control EOF is failure. Success requires the actual original helper exit/close 0 and both EOFs, the unique generation-0 target's original wait/exit 0, atomic Job membership, both target EOFs, Job empty and the native lifetime closure. Native `InputSettled` is a prerequisite of that closure, not inferred from an ACK. Forced termination remains a recorded fact and cannot count as normal shutdown. Abort, malformed output, deadlines and uncertain writes go through the same retained owner and closure path.

The local admission callback is a trusted host boundary, not a remote DTO: it must establish protected immutable broker installation and storage roots before launch and after closure. Its original function reference and pins are captured; callbacks must finish synchronously and return undefined. Promises and thenables cannot authorize launch. A digest or an assertion callback supplied by generated code is not admission. The future node-local profile integration must supply this authority. No HTTP, generated-process channel, compiler/LPAC runner, service rotation, backup, migration, publication or health/recovery policy is provided by this process component. SQLite COMMIT and delivery remain separate; failures retain the store and original idempotency keys, never assert rollback or delete evidence. The owner checks cancellation again after actual writes and immediately before returning a successful reply.

Before a receive batch reaches the bridge, a separate bounded wire decoder validates that entire batch and preserves its own sequence/fragment state. It grants no authority. The host checks a conservative complete reply budget before any database permit: mutation-only transactions use the fixed result shape (1024 bytes for full reply/scope metadata plus 256 per mutation); reads and any transaction containing queries use the broker's existing 262144-byte complete-reply cap. Replays have the same request shape and conflict replies are smaller. Serializing the valid reply JSON inside a wire string expands its UTF-8 bytes by at most two, with 1024 additional bytes for that envelope and both correlation IDs. The budget then includes the four-byte wire header, base64 expansion, array punctuation and the control envelope. Application response bodies and host invocation IDs are included separately.

The complete potential reply must fit both the 1.5 MB control line and remaining 8 MiB output budget. A fixed 512-byte initial reservation covers the ready line. Successful replies charge their actual serialized bytes including the newline exactly once; unused worst-case room is not permanently charged. Large batches or near-limit invocations may therefore be rejected even when the current database contents would produce a smaller result. A receive call rejected by either transport budget precheck obtains no permits and commits no prefix from that call. Entry-level checks remain as independent bounds. An actual pipe failure, cancellation, deadline, later semantic error or violated invariant after a previous COMMIT still means indeterminate delivery; this preflight does not promise rollback or reliable delivery. The earlier r2 implementation could exceed these transport bounds after COMMIT; its failed-before regression and earlier evidence remain retained.

Validation results and exact limitations will be recorded separately after executed checks.
