# Internal application data broker

This is an unintegrated, trusted SQLite component for the planned Windows Node/TypeScript application profile. It does not enable that profile or execute generated code. No worker, HTTP proxy, migration, backup, release or native isolation claim follows from this component.

The host provides an already protected, product-specific database path and a pinned initial schema. `create` exclusively creates a new file; `open` requires an existing store with the same product, data generation, complete schema and current service generation/artifact. Changing the schema or data generation is unsupported and fails closed. Failed files remain in place. Directory ACLs, aliases, file-identity continuity and the launch/closure of a separately owned broker process remain integration prerequisites; this synchronous core is not an OS filesystem boundary and must not run generated code in its process.

Application requests are bounded JSON text. They can read an exact primary key or a primary-key page, insert a complete row, update selected fields using an expected revision, or delete using an expected revision. A transaction contains at most 32 fixed operations and no application callback. Identifiers come only from the pinned schema, values are bound SQLite parameters, and requests cannot supply SQL, expressions, DDL, paths, extensions, filters, joins or executable hooks. Columns support text with a UTF-8 byte limit, bounded safe integers, booleans and explicitly nullable values.

The host-only control API grants an opaque, local, short-lived permit for the complete canonical request digest, read/write access and exact product/artifact/data/service scope. It must not be forwarded to the application's IPC surface. Copying or serializing a permit grants nothing. Read-only health access is enforced by this permission, not inferred from an HTTP method or route name. Permission, expiry, cancellation and the persisted generation fence are checked before work and again in the same transaction immediately before commit. Service rotation uses a persisted compare-and-swap; another connection holding an older generation cannot continue reading or writing.

The one-second execution budget is an elapsed-time check before commit. Synchronous SQLite cannot process an event-loop abort while a statement is running. A future separately owned broker and its original process handle must impose the hard wall-clock limit, cancellation and confirmed closure. This library does not claim that guarantee. `rotateService` changes only the database fence; its caller must separately enforce service draining, ownership and original-process closure before starting a successor. It does not launch or certify a service restart.

Business changes and their idempotency result commit together. A conflicting operation rolls back all business operations in that batch, then persists the conflict result. An operation key is retained for the stable product/data store, including across service/artifact rotation and actual close/reopen. Reusing the key with a different request fails; replay still requires a current valid permit. The original committed scope is retained in the replay result. Deletion leaves a tombstone so deleting and recreating an ID cannot turn an old revision into valid authority.

First-version limits are deliberate: 8 tables, 16 columns per table, 10,000 rows including tombstones per table, 10,000 idempotency records, 64 KiB requests and 256 KiB replies. A store is limited to 65,536 pages of 4 KiB. Tombstones and idempotency decisions consume quota permanently; no pruning, quota reset or data-generation migration is implemented. Primary-key paging may traverse tombstones, bounded by the table quota. Exhaustion rejects the request instead of dropping replay protection. These bounds do not replace process CPU/memory/disk qualification.

The Vitest suite exercises actual SQLite files and multiple connections. The separate `test-fixtures/application-data-broker-real.test.mjs` fixture requires a fresh built module and runs two real workers behind a shared start barrier; it waits for their actual exits before removing its test store. It checks concurrent same-revision withdrawals, followed by service rotation/reopen and durable replay. Failed bodies, unconfirmed closure and timeouts retain their stores; cleanup still attempts every original Worker and broker closure, preserving both body and cleanup errors. These are storage-component checks, not a live-provider product acceptance run.
