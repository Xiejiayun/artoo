# Fixed application compilation core

This is an internal, unintegrated text-compilation component and a type-only SDK draft. Native profile admission, an isolated Node/TypeScript process, protected output staging, actual process closure, node-owned verification and publication remain **unavailable**. No application capability is advertised and no ordinary same-user subprocess fallback exists.

The core accepts complete UTF-8 source and compiler-library snapshots. It does not read a project directory, `.npmrc`, package scripts, `tsconfig`, `extends`, plugins or ambient type packages. It does not install dependencies, access a network, render HTML or execute product code. The Node adapter imports the development TypeScript package; its `compiler_version` is descriptive. `compiler_lib_digest` measures the supplied declaration texts and `sdk_digest` measures the bundled type declarations. None of these proves the bytes of the running Node executable, TypeScript implementation or its dependencies. A future local profile and qualified native runner must bind those actual bytes before any protected build can be claimed.

Supported inputs are `product/client/index.html`, client HTML/CSS/TypeScript files, `product/server/handler.ts` and server TypeScript modules. Assets are UTF-8 text only. There is no bundling, framework, JSX, runtime npm package, image pipeline or HTML/CSS URL rewriting. HTML/CSS are copied verbatim; this is not browser/network/HTML safety validation. Each TypeScript module emits a corresponding `.js` file under a separate virtual `client/` or `server/` output root. The core returns in-memory immutable strings, not a physical staging-directory receipt.

Imports use explicit relative `.js` specifiers resolving to captured `.ts` files within the same client/server subtree. The internal `@artoo/application` module is type-only; it must use `import type` or `export type`, and emits no runtime dependency. Dynamic imports, require, source references, compiler suppressions, ambient modules and explicit `declare` declarations are rejected as supported-format diagnostics. The complete `@ts-nocheck`, `@ts-ignore` and `@ts-expect-error` prefix families are reserved everywhere in TypeScript source, including ordinary strings and prefixes with suffixes. This conservative format restriction avoids missing actual suppression comments after template expressions because a standalone scanner lacks the parser's rescan context. Rejecting explicit declarations prevents an ambient handler value from satisfying the type check and disappearing from emitted code, including through a re-export. These syntax checks are not a sandbox or proof that arbitrary generated JavaScript is safe; the future bootstrap must still validate and exercise the actual runtime export.

Client and server use separate real TypeScript programs with fixed strict options. The client receives ES2023 plus DOM declarations; the server receives ES2023 and the fixed SDK. TypeScript library-reference names resolve only within the supplied library snapshot. A synthetic declaration checks the named `handle` export against the draft handler type. The SDK describes a JSON request/response and bounded data AST adapter for a future trusted bootstrap; it does not supply or certify that bootstrap, IPC transport, HTTP proxy or runtime implementation.

The virtual CompilerHost returns only snapshot content, supplies no project config, and never invokes the ordinary module resolver. During the Node adapter's synchronous compilation call, every callable member of the actual TypeScript `sys` object is replaced with a rejecting guard and restored in `finally`. Thus an internal fallback fails instead of reaching host storage or environment. No plugin, application callback or async continuation is allowed while that guard is active. The entry rejects a present `NODE_OPTIONS` or `NODE_PATH`; this cannot undo a loader that ran before module startup. The future native launcher must provide a whitelisted environment before Node starts. Process memory/time limits and compiler-parser isolation remain native-owner responsibilities.

A successful draft records complete source/library/artifact manifests and their hashes. The local equality check requires the original in-memory draft, an unchanged current source snapshot, and an exact complete output set. Missing, changed, added or case-colliding output fails. Serialized metadata cannot substitute for the original draft and never grants execution or release authority. Physical writes, file identity, ACLs and a final node-owned source remeasurement remain unimplemented.

Diagnostics are capped at 32 entries with fixed messages, numeric TypeScript codes and product-relative locations. Raw compiler diagnostic strings, host paths and source excerpts are omitted. Source is limited to 256 files and 8 MiB total; library text to 128 files and 16 MiB; output to 16 MiB. These byte bounds are not hard process CPU/memory limits.

The original tests use the real compiler for normal cases and one explicit `sys` fallback fault to verify fail-closed behavior. They cover configuration/plugin rejection, environment loader settings, references and module escapes, type failures, handler typing, separate DOM scope, missing libraries, source/output mutations and no product execution. Before the shared-kernel extraction, this worktree installed its own locked dependencies and passed workspace type checking and a fresh TypeScript project build (`tsc -b --force`). The compiler, broker and wire focused suites passed **92 tests** together, with no skips; see the [focused log](../../../artifacts/application-component-validation-r1/focused-r1.log). No prior worktree's dependencies or built modules were reused. Those earlier results do not validate the later extraction.

Native/profile integration and repository-wide checks remain separate later gates. These executed component tests do not establish native compiler isolation or generated-product execution.

The [validation record](../../../artifacts/application-component-validation-r1/VALIDATION.md) also records the 6 real SQLite Worker checks and, separately, the storage-timeout parent regression that accepted 5 intentional child failures and 2 passes. Those checks do not qualify the compiler's native runner, a broker process, HTTP delivery or model-driven product development.

## Shared kernel and guest preparation

`application-build-kernel.ts` now owns the single source of schema, policy, fixed options, handler typing, diagnostics, complete manifest and draft-identity logic. `application-build-core.ts` preserves the public API and supplies the trusted local Node adapter. The factory captures local primitive functions; a compile request cannot choose them or create a different draft owner. Every owner has its own WeakMap, so a serialized or cross-adapter draft fails the identity check.

The fixed QuickJS guest entry uses that same kernel, SDK and packaged library snapshot, with guest-local UTF-8, SHA-256 and virtual POSIX functions. It requires the reviewed TypeScript version, no `ts.sys` and no Node/network globals. Its only exported operation accepts a request JSON string and returns the complete response, including all manifest digests. It validates with the complete original kernel schema and checks the same 52 MiB request and 100 MiB response definitions. No host hashing/path callback or product-code evaluator is supplied. The transport and native owner remain separately unqualified.

The guest packager writes a fresh package containing the exact reviewed TypeScript bytes, one shared-source guest bundle and a measured manifest. New tests prepare independent Node comparisons for Unicode/surrogates, SHA padding and long input, virtual path traversal, whole-draft equality, independent source/library/SDK/artifact digests, unchanged failure semantics and owner identity. The real QuickJS fixture compares complete responses and recomputes all successful manifest fields from independently pinned input snapshots. Emitted JavaScript is never run.

The extraction, new tests, guest package and fixed parity child are source preparation only until separately executed and recorded. The earlier four-case QuickJS compatibility diagnostic compared output/diagnostic subsets; it does not validate this complete-manifest path. No dependency version, process budget, source allowance or product capability is increased by this draft.

## Host compiler response capture

`application-compiler-response.ts` parses one bounded UTF-8 response followed by EOF. It rejects unsupported fields and shared, resizable or detached byte storage. This host module is separate from the original compiler protocol and is not imported or re-exported by the packaged compiler entry; the fixed packager's source allowlist remains unchanged.

`createApplicationCompilerCaptureOwner` copies the original request and locally selected compiler version/library content. A captured result must match the request ID, exact source and library pins/digests, fixed SDK digest, complete output path set, recomputed artifact pins/digest and verbatim HTML/CSS assets. Each owner permits one capture attempt, including failures and rejection. Captures are opaque owner-local tokens; forged, foreign and revoked tokens fail, and reads return deeply frozen content. This is not a durable or global replay registry.

The captured value remains `scope: "compiler-response-content-only"` and `qualified_for_product: false`. Self-consistent response content does not prove which compiler ran, executable/package identity, or that compilation caused the output. EOF does not prove original process or Job closure. The deserialized draft still fails the kernel's `local-draft-required` check. Protected toolchain admission, native process ownership, deadlines and closure, immutable staging, node-owned verification, independent review and publication require separate integration; this capture grants none of those authorities.
