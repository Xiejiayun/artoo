# Trusted application invocation bridge

This unintegrated host component combines the existing application wire format and SQLite data broker. It runs no product code and opens no process, pipe, socket or HTTP listener. It is not connected to node admission or native execution, and the native application qualification gate remains closed. The future owner must keep the bridge and broker in a trusted process separate from generated JavaScript.

One bridge belongs to one original application data-channel lifetime and one immutable product/artifact/data/service scope. The host chooses its maximum read/write access. `begin(requestJson, policy)` is a **host-only** API: it assigns a unique call ID and returns an original opaque invocation handle plus an encoded `invoke` frame. Neither the handle nor the policy goes into the application DTO. The JSON request text is bounded by bytes and nesting before it is parsed as a complete independent value; only that parsed data is serialized inside the envelope. Appending envelope fields to the text cannot replace the host's call ID. The existing encoder still validates the complete request and envelope graph.

`receive(chunk)` accepts ordered bytes from the original application-to-host stream. It preserves the wire decoder's sequence and strict-field checks, then binds every response or data call to a live invocation. Application-supplied call IDs are correlation data, not a way to start an invocation or select scope, permissions, a database, SQL, a command or a permit. The original host handle is returned with a completed response. Copying, serializing or borrowing a handle from another bridge does not grant host control. A response ends that invocation; later input for it rejects the session.

Data-call IDs must be unique **within their invocation**. They may be reused under a different host-generated call ID. Old call IDs are never admitted again during this session, and all ID/call state is bounded. A fresh data-call ID may repeat an idempotency key with the exact request; the broker's durable ledger, current permit and generation fence decide that replay. A replay result's original scope is informational and does not become authority.

For each data call the actual broker validates the request against its own pinned schema. The bridge checks the host access policy, preflights the maximum reply graph and output quota, and only then grants a short-lived permit for that exact canonical request digest, captured scope and invocation signal. `execute()` uses that original permit, and `finally` revokes it on success or failure. Expected malformed-request, conflict and storage-quota errors return only the broker's fixed error codes. Scope, broker lifecycle, clock or channel failures terminate the bridge and revoke its remaining invocations. No grant, rotation or host-control method is present on the application's wire surface.

Health and peer invocations are admitted only with read access **on a bridge whose maximum access is read**. A writable bridge rejects these purposes even if the individual invocation asks for read. HTTP methods and route names never grant permissions. The future owner must use an independent read-only process/channel for these checks and must not expose another write channel to the same generated process while claiming that health or peer work is unable to write. Correlation IDs alone cannot prove which concurrent handler caused a request.

The host can call `cancel(handle)` or schedule `poll()` to retire aborted/expired invocations and produce cancellation frames. These are synchronous authorization checks, not native deadlines or a wall-clock watchdog. Every data admission and successful result delivery rechecks current scope, signal and time. The broker retains its own relative permit lifetime and precommit checks. A synchronous database operation cannot be interrupted by this component's event loop; expiration observed after COMMIT suppresses the successful delivery but does not undo the committed transaction. No hard absolute commit-deadline guarantee is supplied here.

Local rotation of the same broker object is detected at every bridge entry. Rotation through another connection is caught by the broker's persisted fence before data work. `getScope()` does not read that persisted fence, so a response containing no data call is **not** evidence that the store's lease remains current. The future owner must revoke/drain the old bridge before service rotation and establish original process closure separately; the bridge does not rotate or reopen stores.

Limits are fixed: eight active invocations, 256 invocations per bridge, 32 data calls per invocation and 2,048 in total, 4,096 incoming frame headers, 16 MiB of raw input and 32 MiB of framed output per bridge, and 1 MiB incoming / 4 MiB outgoing per invocation. Raw input includes malformed/unknown-call bytes; per-invocation accounting includes complete raw frame sizes and JSON whitespace. Invalid input terminates the stream rather than resetting its counters. Retention of unfinished frames stays with the existing bounded decoder. Before any database grant, the bridge reserves room for the largest legal wire reply against both output quotas; it rejects conservatively near the limit. The transport owner still owes bounded OS reads, write queues, backpressure, lifetime/output enforcement and native resource qualification.

The reply-graph preflight uses the fixed broker result shape and the wire's entry definition. Reply/result/scope contribute 23 entries. A selected row contributes one array element plus two entries per selected column. Each committed mutation contributes seven entries, while each query operation contributes five plus its possible rows. A read therefore has an upper bound of `23 + limit × (2 × columns + 1)`; a transaction uses `23 + sum(mutation: 7; query: 5 + limit × (2 × columns + 1))`. Conflict and replay results cannot add another shape. Requests whose declared maximum exceeds the unchanged 16,384-entry wire limit are rejected before obtaining a permit, even if the current data would happen to contain fewer rows. This explicitly restricts the bridge's supported subset of the broader broker AST.

Database effects and reply delivery are separate. A later semantic error in the same `receive()` call can reject that call after an earlier request committed. An output/expiry failure can also leave a committed result without successful delivery. The host must treat this as indeterminate delivery and preserve the original idempotency key and store; it must not report rollback, silently create a new operation key or infer release success. The decoder's rejection of an invalid framing batch still returns no parsed prefix to this component.

`close()` is terminal host revocation and emits one shutdown frame. It does not allow subsequent `receive()` or `finishInput()`, close the broker, drain native pipes, wait for a process or certify a Job. `finishInput()` is only the caller's framing-EOF declaration; an incomplete frame or active invocation fails. The future owner must independently perform bounded drain and observe original pipe/process/Job closure even after this bridge has failed or closed. Neither method authorizes deleting a store or publishing a product.

The component tests use real SQLite and the real wire encoder/decoder, with explicit synthetic clock seams for deadline races. They cover opaque authority, request-envelope injection, read-only health/peer sessions, strict correlation, replay and rotation, all implemented call/byte quotas, cancellation/expiry, post-COMMIT delivery failures and exact reply-graph boundaries. Validation and retained failures are recorded in `artifacts/application-invocation-validation-r1/VALIDATION.md`. These tests do not establish native isolation, an independently owned broker process, IPC integration, HTTP behavior, model-driven development, release health/recovery or publication.
