# Stage the daemon with browser approval

Use the manually dispatched **Stage daemon on npm** workflow when the build machine cannot reach the npm registry. It runs only from `main`, uses npm 11.20.0 and the official registry, and uploads an already validated tarball. It does not rebuild the package or claim GitHub build provenance.

1. For the universal candidate (`0.1.0-rc.2` onward), require a successful **Build and verify cross-platform npm daemon** run from a `push` to `main`, or manually dispatch `.github/workflows/npm-daemon-cross-platform.yml` on **main** with the exact version. It builds a fresh Windows x64 native host and one tarball, then installs those identical bytes without `--force` or `--ignore-scripts` on Windows x64, macOS x64/arm64 and Linux x64/arm64. Require the aggregate job and all five platform jobs to pass. Retain the candidate tarball, `release-metadata.json`, `cross-platform-summary.json`, five platform reports and separate POSIX fixture logs. Bind the exact SHA-256, SHA-512 integrity and source commit to these results. A PR merge-ref build is validation evidence only; rebuild and validate on main before delivery.
2. Create a **draft release in this repository** and attach that unchanged `jiayunxie-artood-<version>.tgz`. If its tag does not yet exist, set the draft's target to the full 40-character source commit recorded by the successful main build. If the tag exists, it must resolve to that source commit. The resolved source must already belong to `main` history; do not attach a different build to a convenient main tag. Keep the validation receipts alongside the release evidence.
3. Dispatch `.github/workflows/npm-daemon-release.yml` on **main**, supplying `release_tag`, exact `version` and the recorded SHA-256. No npm token secret is required. The workflow checks the draft/source relationship, file digest, fixed package name `@jiayunxie/artood` and publication metadata before authentication.
4. Open the **Log in through the official npm website** step's live log. Use Edge to open the official URL printed by `npm login --auth-type=web --browser=false` and authorize the CLI as **jiayunxie**. The login command has a 15-minute limit. Do not copy tokens or browser cookies into Actions.
5. After the run reports a stage ID, review that exact package/version under **Staged Packages** on the npm website. Complete the website's approval and 2FA step separately. A successful Actions run means **staged**, not published. New package staging may create the npm `0.0.0-stage` placeholder; this is not the final version.
6. Confirm the final version and `next` dist-tag on npm, then perform a fresh registry installation of the exact version on each supported platform. Compare the registry/lockfile SHA-512 integrity with the validated tarball, run the installed manifest and CLI checks, and repeat the connection/task/normal-stop smoke. Record registry origin, version, OS/architecture, Node/npm versions and actual command results. The cross-platform workflow installs its candidate tarball, so its success alone is not post-publication registry-installation evidence. Do not describe staging or a placeholder as an available final release, and do not recommend unversioned installation while `latest` points elsewhere.

The cross-platform build/check workflow has read-only GitHub permissions, no npm credentials and no publishing step. Its controlled Codex/Claude success/failure fixtures do not invoke a real provider. POSIX process verification runs separately against built repository modules; it is not native Windows qualification, browser acceptance or deployed-product health evidence. Windows arm64 remains unsupported even though npm's coarse OS/CPU fields cannot represent that exclusion.

Linux enrollment also requires the matching server/Web upgrade and ordered database migration `0056_linux_devices.sql`. Complete the server backup and migration/recovery plan before deployment; publishing or installing the daemon does not upgrade the server. Do not roll back to the older platform constraint while Linux device or pairing rows remain.

The published Windows-only `0.1.0-rc.1` and its `registry-smoke.mjs` evidence remain historical. That script is deliberately pinned to rc.1 and does not qualify the universal candidate. The staging workflow still accepts the original Windows-only manifest, while universal metadata must declare the exact five supported platform/architecture pairs.

The workflow defaults to read-only GitHub contents permission. Its manual, main-only staging job requests `contents: write` because [GitHub requires push access to see draft releases](https://docs.github.com/en/rest/releases/releases#list-releases). This temporary token can write this repository's contents; it is exported as `GH_TOKEN` only in the draft download step, checkout does not persist it, and npm steps do not receive it. The job does not mutate GitHub releases and has no OIDC permission. Inputs enter scripts through environment variables. Candidate metadata is read from the tarball without extracting or running its scripts. The official npm CLI uses a fresh user config/cache under this run's `RUNNER_TEMP`; there are no long-lived npm credentials, proxies, TLS overrides or automatic stage approval.

An `always()` step attempts `npm logout`, which revokes this CLI session, and then removes only this run's temporary directory. If logout fails, the job reports an error even if staging succeeded; revoke that session in npm account settings. A forcibly terminated runner can prevent cleanup, so an interrupted login should also be checked in npm account settings. The workflow does not upload credential files or npm logs as artifacts.

Reference: [npm staged publishing](https://docs.npmjs.com/staged-publishing). npm 11.20's `StagePublish` inherits the normal publish command's tarball handling and options, selects the staging API, and defers proof of presence to approval. This workflow intentionally uses `npm stage publish <exact-tgz> --tag next --access public --ignore-scripts`, followed by logout; it never invokes `npm stage approve`.
